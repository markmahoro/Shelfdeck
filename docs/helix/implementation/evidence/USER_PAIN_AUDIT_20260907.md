# 五项用户痛点审计与迭代方向

2026-09-07。状态：只读审计完成，迭代建议待评审；非 Canonical，不修改 SSOT，不授权实施或生产操作。

## 结论

五项痛点可以由三组具体问题解释：工作展示没有覆盖所有实际工作；已有底层限流没有形成用户可理解的批量改善队列；列表读取、文件验收与外部软件共存的合同超出了必要成本或缺少结果收尾。

不以此前“Aftercare 委托 Libra Run”作为本审计前提。当前证据不要求先合并两个生产体系才能解决这些痛点。优先交付统一工作可见性、可控的批量改善和有界读取，再收缩 NFO 呈现校验与补齐源目录处理合同。

| 痛点 | 审计判定 | 主要依据 |
| --- | --- | --- |
| Aftercare 不在媒体整理页 | 已证实；收藏详情已有局部进度，并非完全没有业务记录 | FormationPage/API 只有 Formation，CollectionPage 单片弹窗读取 Care |
| Aftercare 无节流、改规则会雪崩 | 前半句需修正：有资源/Work 硬上限；缺少独立的跨 Entry 改善准入和可见积压。雪崩是风险，未复现为事实 | 256 Work/Event 上限、逐 Entry 单 active Case、GPU/磁盘 Permit、周期预算均存在 |

## 2. 工作可见性：问题在产品入口覆盖范围

### 证据

- `media-service/web/src/helix/FormationPage.tsx:10` 的账本类型只有 `formation` 和 `ended`；加载只调用 Formation active/completed/history。
- `media-service/web/src/helix/api.ts:630` 起的 Formation API 与 `:658` 的 Care API 分开。
- `media-service/web/src/helix/CollectionPage.tsx:12` 已定义 Aftercare 阶段文案；`:103` 附近只在用户打开具体收藏弹窗后读取 Care，存在 activeCaseProgress 时约 2 秒刷新，否则 15 秒。
- `media-service/src/helix/domains/arca/application/aftercare-process-coordinator.js` 的 `caseProgress` 已输出目标、阶段、媒体进度；所以不是需要凭空新增执行事实。
- SSOT §9.4.6 明确将媒体整理工作区限定为 Handoff A Accepted 开始的 Formation。当前 UI 与既有合同一致，但合同不符合用户现在对“整个 ShelfDeck 工作区”的预期。

### 用户影响

用户必须预先知道哪部收藏正在改善，再逐部打开详情，才能看到后台工作。媒体整理页“没有工作”不能代表系统没有工作；创建 Case 之前的评估、等待，以及终结后的整体结果也缺少统一入口。信任问题成立。

### 建议

将媒体整理页的展示合同扩展为统一工作入口，而不是建立新的全局业务状态机：

- 类型至少包括新媒体整理、已上架改善；例行轻量检查按批次汇总，实际写文件/转码/下载必须有可追踪事项。
- 每个事项显示影片、触发原因（例如编码标准变化）、目标差距、当前动作、等待原因、真实进度、开始/结束时间、最近更新时间及结果。
- 统一“排队中 / 执行中 / 需要处理 / 已完成”用户分类，保留底层 Owner 和原始业务状态映射，不把排队显示成转码中。
- 收藏卡片和详情提供工作入口；同一 Case 的多次技术尝试合并展示，失败原因与恢复结果保留。
- 以 `owner + process kind + process ID` 区分工作，不伪造 Subject/Run，不要求改动 Libra/Arca 生产边界。
- 分别展示“当前产品是否可用”和“是否满足新要求”，不要把尚未评估、环境不可达和已损坏统一表示成不健康。当前 `foldedHealth` 会把 healthy/repairing 之外都折为 unhealthy，容易放大用户不安。

## 3. 批量改善：有底层保护，缺少业务准入

### 已有保护，不能漏算

- `aftercare-process-coordinator.js:10` 使用 `globalOpenWorks:256, ownerOpenWorks:256, openEvents:256`。这是 Work/Event 上限，不是“最多 256 个转码”或“每 Shelf 256 个 Case”。
- `aftercare-store.js:120` 起检查同一 Entry 最多一个 active Case；不存在单 Entry 无限制创建。
- `foundation/execution/work-admission.js:179` 起按当前 Work/Event 数执行硬上限。
- `composition/create-procurement-execution-runtime.js:658` 起为 Aftercare 要求 volume_read/write、cpu_heavy 和具体 encoder 槽；不能称它绕过 Resource Governor 无限制并行转码。
- `foundation/execution/domain-reconcile-runner.js:12` 起默认一页 100、每个注册器预算 5 秒、周期 30 秒，并在每个 scope 后让出事件循环。预算不是整个系统全局 5 秒，也不能中断一次已经开始的同步调用。

### 缺口

- Case 创建只检查单 Entry、当前依据和 Off-deck 等阻挡条件；没有跨 Entry 的 Aftercare active Case 席位、每 Shelf 队列或独立积压可见性。
- Standard revision 会进入每部影片的 Care Basis。批量修改可使很多 Entry 需要重评，进而陆续形成 Work/Case；资源等待限制重活并发，却不等于限制活跃业务事项及其上下文/历史读取、规划、重试和工作区占用。
- 各协调器传入的 Work admission 数值并不统一（存在 256 与 1000 等），不能仅看到某一处 global 字样就把它当成整个应用一致的预算。
- Aftercare 与 Arca Acceptance/On-deck 使用同一业务 Owner 维度，缺少明确的改善工作与交付工作的公平性合同。是否已经造成饥饿需负载证据，不在这里宣称。

### 建议

采用三层控制，复用已有调度器，不另起一套执行引擎：

1. 评估排队：标准发布先持久记录待评估范围，合并同 Entry 的重复触发；分页评估并限制每轮耗时，不在配置请求内逐片创建全部工作。
2. 改善准入：仅小批量事项取得执行资格并创建生产工作区；其余维持轻量队列。首轮建议保守从全局 1 个重型改善事项起步，具体默认值须由 NAS 混合负载验证决定，不能冒称现有配置。
3. 资源执行：继续使用 CPU、编码器、磁盘和集成 Permit，并给首次上架、后台改善、轻量观察建立明确公平性；限流等待不消耗失败重试次数。

规则再次变化时收敛到最新有效目标，不反复为每个中间 revision 启动重活。用户应看到受影响数量、待评估/排队/执行/完成数量以及预计资源后果。建议提供“停止继续接纳新的自动改善”能力；已开始的安全收尾与待接纳分开定义，不引入任意暂停内部 Event 的按钮。是否提供这一用户开关需作为产品合同确认。

## 4. 页面慢：先修读取路径，不靠清理数据库掩盖成本

### 整理页

- `FormationPage.tsx:177` 起首屏同时请求 active、completed、ended、Shelf 和 Perception 状态，受最慢依赖影响。
- 首批结果会先显示，这是已有优化；但 `:211` 随后仍遍历剩余分页，各循环最多允许 399 个 cursor。用户未打开历史也持续读取全部历史。
- `:222` 只要存在 in_progress，就每 10 秒再读三个账本首批；后台分支没有单次在途请求保护，请求超过周期时可能重叠；这是一种风险路径，未证明现场已发生重叠。
- `formation-query.js:756` 起列表读取先用 `detailSource.getMany` 补最新事实，再用 `getManyWithProcessSummary` 生成摘要。
- `:511` 起即使只是摘要也读取 `includePlans:true` 的执行图，包含关联 Procurement Run ID；一个历史采购 Run 可以包含很多 Candidate，不能认为这个读取成本必然只限于当前一部电影。
- `clean-service-host.js:1464` 确实注入该 detailSource，所以不是没有启用的备用代码。

### 收藏页

- 前端已经按 48 项分页；不能建议“加分页”就当解决了。
- `collection-query.js:167` 只在 recent、无搜索、无健康筛选时先截取页面。标题/年份排序、搜索或健康筛选会对所选范围先装配资料和健康，再分页。
- `collection-query.js:140` 的批量缓存按 Entry ID读取所有相关 revision，然后在内存挑当前 revision；比逐条 SQL 好，但仍受历史增长影响。
- `aftercare-store.js:184` 起健康批读包含全部相关 Assessment、Finding、Case 与 Inventory 历史，随后排序、归并。当前快照只有 54 部却已有 577 条 Assessment；历史增长会增加列表成本，不能以 54 部规模推断查询必然很轻。
- 收藏详情 Care 高频刷新还会读取 case/history/progress；进度刷新不应反复携带所有历史。

### 建议

- 列表使用紧凑的当前状态投影；实际步骤图和历史按展开需求读取，避免每次列表刷新重建全流程。
- 所有搜索、排序、健康过滤均在可索引当前摘要上分页；统计单独缓存或维护，返回 freshness，不在每次翻页重新回放历史。
- 整理页历史按需翻页；活动摘要采用单请求在途、可取消和可见页刷新，避免轮询叠加。不要只是降低刷新频率掩盖重查询。
- 主内容首屏不等待可独立呈现的配置/辅助面板；图片尺寸、传输和浏览器渲染仍须测量，尚不能认定图片不是瓶颈。
- 改善队列、健康列表和执行状态均从 durable facts 派生；投影滞后明确展示，GET不做业务修复。

### 性能验收建议（目标，非现有测量）

先采集真实 NAS 的 API 分段耗时、SQL数量/行数、事件循环延迟、响应体、海报加载和浏览器首屏，再用相同样本比较。

- 在约定 NAS 与局域网环境、正常生产负载下：首批列表 API p95 ≤ 500 ms，主要列表内容可见 ≤ 1.5 s；达不到时必须提供瓶颈证据并重新校准目标。
- 页面取 48 行不回放全量执行图/Assessment历史；历史增长 10 倍时，普通列表查询成本不线性增长 10 倍。
- 首屏不下载全部历史；任一刷新流同时最多一个请求。
- 同时跑新片转码、批量改善及两页浏览，验证有界队列和响应时间；当前停机审计不替代该运行验收。

## 5. Top Gun：完成范围与外部播放器看到的目录不一致

恢复后快照显示最终目录有主片、NFO、poster、fanart、字幕及一个已纳管 `.srt.csf-bk`。旧目录 `/media/Film/Top Gun - Maverick - IMAX (2022)` 有 torrent、Thumbs.db 和 9 张长文件名图片，没有第二份主片。

原 Off-load Context 的主片名是 `Top Gun - Maverick - IMAX (2022) 2160p EAC3 Atmos.mkv`；残留图片使用 `Top.Gun.Maverick.2022.IMAX.2160p.WEBRip...` 的另一文件名前缀。

`procurement/model/triage-contracts.js:303` 起 `relatedFor` 只接受标准附件名或当前主片/目录标题同 stem 前缀。长图片名不是裸 poster/fanart 等标准名，也不匹配当前主片或目录 stem；据当前规则不能进入 Related Scope。它们不在该 Off-load Context 清单中，不能简单归结为 Arca漏移动已接收文件。历史上何时、由谁写入这些图仍未证实。

SSOT 的 Candidate disposition amendment 要求精确独占 Related收口，同时允许未知/共享项留在 Field，且不授权空目录删除。因此“包内成员全部完成”与“Emby扫描根内不留像电影的空壳目录”是两个不同验收结果。用户指出的是后者，确实没有被当前完成定义充分覆盖。

方向：

- 补齐可确定附件关联的召回和歧义说明，不采用同目录一律归属或按相似片名整目录删除。
- 正常完工提供源位置残留摘要；在外部库扫描根内留下无主片但有电影外观的目录，应有明确完成后收尾结果，而非静默成功。
- 对明确归属的附件执行已授权 carry/settle；对无法归属的文件提供保留/移至扫描范围外的审阅方案，精确列出路径、目标及恢复方式。隔离属于文件移动，不因本审计或用户报告而自动授权。
- 空目录清理与 torrent/系统杂项策略须明确，不能靠增加模糊匹配扩大删除范围。
- Emby侧验证必须核对具体 Item ID、Path、媒体流和刷新后结果，区分仍扫描到残留目录与旧索引缓存；“无主片”本身不足以证明其扫描规则。
- Procurement应继续发现真正的主媒体，不为附件目录制造影片；重复影片判断与目录残留分开。后续独立任务补历史归属链和 Emby证据。

## 6. NFO：收缩呈现一致性，保留文件安全与正确影片识别

### 已证实的阻塞链

- `clean-arca-inventory-port.js:1617` 起 `verifyFinalObservation` 对 Movie NFO使用已接受 metadata/cast/identity比较，失败抛 `CLEAN_ARCA_FINAL_NFO_SEMANTIC_DRIFT`。
- `aftercare-nfo.js:331` 比较影片身份、部分 owned字段和所有要求的演员关系；actor不匹配会返回 actor_missing。
- `aftercare-capability-ports.js:426` 将上述差异转换为自动修复 Finding；`:452` 生成新NFO或执行语义身份协调。上架验证和后续维护共同维持内部资料与外部文件的一致性。
- 8部历史问题是演员Person ID被写为Movie ID，符合已修复的旧Libra渲染器缺陷；3部是同inode字节变化但语义有效。没有证据证明每次改写都来自Emby，也没有本轮在线证据量化“往返次数”。

### 价值判断与建议

演员/剧情等呈现字段不一致就阻断一部可播放影片的上架，代价高于当前用户收益；这一默认合同应当收缩。不能把“比较已有NFO每个字段”和“防止删错输入或收错影片”混为一类。

| 场景 | 建议保留 | 建议取消或降级 |
| --- | --- | --- |
| 输入识别 | 需要时读取NFO影片身份，冲突不猜测 | 不要求所有资料字段齐全才允许发现 |
| 本系统生成NFO | 生成器正确性、非空、可读、基本格式正确 | 不为已有外部描述差异无限重写 |
| 首次落盘验收 | 正确文件位置、存在与基本可用；主片身份和真实媒体要求单独保证 | 演员/剧情等外部呈现差异不作硬上架阻断 |
| 上架后维护 | 必需文件丢失、不可读取；规则变化相关的真实媒体差距 | 周期性逐字段纠正、把每次NFO字节变化当作内容损坏 |
| 删除/替换旧文件 | 精确目标、权限、当前操作前证据、可恢复副作用 | 不能因取消语义校验就忽略文件已被外部改写 |

资料文件允许外部编辑后，必须同步修订 Binding/Material Control对NFO变化的解释、旧输入处置和人物证据采集；不能只删一个 comparator。周期NFO解析若承担People观察，需保留受控的显式/变化触发证据入口或明确产品损失，不能静默丢掉人物功能。

主片损坏/丢失、错误影片身份、覆盖冲突和删除目标保护仍有明确用户价值。常规无变化文件优先复用证据，发生生成/转码/复制后做针对性验收；没有本次计算占比测量，不宣称“删NFO检查就能解决页面慢”。

## 7. 建议迭代顺序与验收

以下是交付顺序建议，不是新活动实施计划；实现前需在唯一 CURRENT_PLAN/CURRENT_PHASE 承接具体授权。

### 第一批：看得见且页面可用

统一媒体工作入口纳入Aftercare；列表摘要与执行图分离；停止自动拉全历史；收藏查询真正按当前摘要过滤分页；补API/浏览器测量。工作必须能追溯到真实Case/Work，等待原因可见，正常用户不需逐片猜后台在做什么。

验收：新片整理和Aftercare同时运行时工作区两者均可见；进度与原生证据一致；完成与失败可追溯；页面满足同环境性能目标。无需预先合并Libra/Aftercare。

### 第二批：大批规则变化可控

标准发布影响摘要、轻量待评估队列、跨Entry改善准入、资源公平性、重复触发合并及停止继续接纳的用户语义。第一批与此批应在生产恢复大量自动改善之前共同完成，不能只上可见性然后放开批量负载。

验收：大量影片同时受影响时只接纳限定数量重活，其余显示排队；不会因等资源变成失败；规则连续修改不重复开工；新片上架与浏览仍可用；重启恢复队列不重复副作用。

### 第三批：文件共存与完成结果

先确认NFO职责收缩的合同，再同步取消相关硬阻断/自重写链；同时接入Top Gun独立排查的源位置收尾方案。这两个子项均需精确的文件操作验收，但不要求在同一代码变更里实施。

验收：外部合法编辑NFO不会来回改写或因演员差异卡上架；NFO缺失/空文件仍按约定被发现；主片错误和删错风险仍被拦住；成功整理不会静默留下未解释的扫描根空壳，Emby刷新后有对应验证。

NFO当前阻塞可作为此批的先行合同议题，与第一批开发准备同步推进；不必等所有性能工作完成才讨论。旧54部的实际维护与新行为改造继续分开授权，不能用再次退收藏或Reset代替产品修复。

## 8. 决策边界

需回到设计确认的内容：媒体整理页覆盖范围（SSOT §9.4.6）、Aftercare跨Entry准入和用户停止接纳行为、NFO呈现与文件身份/人物观察合同、扫描根内未知残留的处置权限。

有证据的工程优化：按需分页、当前摘要查询、批量当前revision读取、避免重复执行图构建、轮询在途保护、性能观测。若具体实现涉及持久投影/表合同变更，仍按既有合同治理传播，不偷改SSOT。

本轮不采用Aftercare→Libra Run、职责合并、Procurement外部寻源或新增全局流程引擎作为既定方案。只有上述用户验收仍无法以现有职责解决时，再基于证据讨论更大范围重构。
