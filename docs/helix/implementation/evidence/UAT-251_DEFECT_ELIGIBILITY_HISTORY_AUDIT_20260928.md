## 当前实现的具体问题

### 1. 自动和手动已共用资格，问题不在两套授权流程

`libra-run-admin-service.js` 的自动处理先读取同一 `defectCandidate()`，持续授权 enabled 后调用同一 `admitWithDefects()`。Manifest 记录 manual / standing 来源。当前需要收敛的是双方共同使用的资格判定，不应新增“自动严格、手动宽松”的两套产品标准。

### 2. 寻源失败可以连带豁免本地可加工要求

`defect-admission-contracts.js::externalDefect()` 使用原片 Verification 的完整 reasonCodes，只要均在宽泛 WAIVABLE_MEDIA_CODES 内就加入授权。缺 4K/音轨导致寻源后，原片同时存在的非 HEVC/容器问题会一起被接受。

《阳光灿烂的日子》的历史结果准确落在此路径：sourceFailureCode=no_available_candidate；实际豁免 container_unmet / minimum_raster_unmet / primary_audio_unmet / video_codec_unmet；authorizationSource=standing。一个 external_source_exhausted defect 实际包含四项要求差距。此处不能把类别数量当作具体缺陷数量。

### 3. 资格已从特定业务场景扩成通用差距

`libra-run-admin-service.js` 依据 Work 类型设置 productGapPaths。`metadataDefect()` 在 metadata 路径可跳过原先特定失败代码/业务失败分类条件；`externalDefect()` 在 media 路径可跳过外部寻源耗尽条件，并生成 media_requirements_unmet。

附件路径会识别 nfo / poster / fanart，`buildDefectAdmissionCandidate()` 直接形成 artifacts_unavailable。该路径并非最初演员为空场景的自然等价扩展。

未配置/当前不可用策略经有限 availability 观察，也能通过 candidateGapSources 形成资料或媒体候选。它没有把代码名伪造成 external_source_exhausted，但接纳门槛已不再要求原来“真实外部路径有效运行且耗尽”的同一条件。

上述是可达代码分支结论，不声称所有技术失败都必然能完成 Arca Commit；后续播放、精确差距、Control、安全等检查仍存在。

### 4. 范围扩张贯穿验收与维护，不能只修按钮

Arca 的 Authorized Manifest 校验、实际 Gap 覆盖和缺附件处理已经接通新类别。`accepted-gap-contracts.js` 中，收藏后新增接受差距也涵盖编码、容器、资料和从未登记的 NFO/poster 缺失；已登记后消失的文件仍被保护为新损坏。

因此纠正时须传播统一业务资格到 Libra、Arca 接纳以及相关测试。Owner 仍各自负责，不创建跨领域 Store 或转移决定权。历史已 Commit 事实不能直接因新规则回写、删除或自动重跑。

### 5. 测试已经把扩大行为当作正确结果

`uat251-exact-defect-gaps.test.js` 明确用 container_unmet / video_codec_unmet 验证 media_requirements_unmet 可形成候选；UAT-251 Evidence 将自动组合差距及缺海报入库后修复作为通过场景。

这些测试证明实现符合当时写下的测试预期，不能证明预期正确反映用户标准。单纯重跑既有测试不会暴露本轮指出的业务问题。

## 用户确认的统一模型与路径规划方向（2026-09-28）

来源：聊天 `01a0e5df-383d-7dc0-8b8a-dc9fb10bf1ab`《分析〈阳光灿烂的日子〉入库》。本节为用户决定记录，不是平行实施计划，不代表 SSOT/派生合同传播、实现、部署或 UAT 关闭。

### 已确认：一套次级标准，只有两个可放宽维度

用户明确：“可以放宽的次级标准 其实还是只有体积 和 演员关系”，并确认与是否发生外部寻源没有关系。

- Shelf Spec 是正常入库标准；瑕疵入库采用从本次 Shelf Spec 派生的次级标准。
- 次级标准只放宽体积上限、演员关系：沿用已确认的质量保护下体积超限、演员确实无法取得条件。具体 typed 证据与执行合同在后续设计中收口，不能仅凭路径失败推导条件成立。
- HEVC、容器/扩展名、分辨率、音轨、海报、NFO、其他必填资料和安全要求保持 Shelf Spec 原要求。
- 这明确取代本聊天前面一度确认的“寻源后可接受分辨率/高质量音轨不足”方案。该早期方案不得继续作为实施依据。
- 自动与手动只改变授权方式，共用相同次级标准；达到次级标准后，自动授权开启则自动接纳，否则等待用户确认。
- 外部寻源是达成标准的手段，不是瑕疵类别或降低标准的理由。不得继续用 external_source_exhausted 对原片规格整包豁免。

### 已确认：统一评估和有限再优化

按 Shelf Spec 处理后：满足则正常入库；不满足则评估次级标准。直接满足次级标准则进入瑕疵授权；尚不满足但存在达成可能性，则自动触发面向次级标准的再优化；无法达成则本次无法入库。

接续 Run 是此前助手建议：保持同一个用户整理条目，原 Run 冻结依据及历史不改，接续 Run 绑定次级标准并复用有效材料/成果。用户尚未单独定稿该实现选择；不得将其记录为已经确认的 Run/Workspace 生命周期合同。不得擅自增加无限降级、递归派生或同条件反复寻源。

### 已确认的问题方向：外部材料可经内部加工达标

用户指出：《阳光灿烂的日子》的外部候选未必是最终合格成品，应考虑“外部寻源 + 内部转码”组合达成 Shelf Spec 或次级标准，需要审查路径规划。

- 不能仅因外部候选当前非 HEVC，就无条件等同于无法得到合格产品；应讨论候选作为加工输入后的达标路径。
- 本次历史候选中的 H.264 / 被声明为 4K / DTS-HD MA 项，是评估组合路径的线索，不是已证明可用的产品：身份尚未通过匹配，4K 来自简介文本识别，未下载或实际 Probe。不得保证该片一定能成功。
- 候选选择条件、声明证据充分性、可加工差距、真实 Probe 后规划、单来源有界性、质量保护、失败收尾以及正常/次级目标之间的关系，均需继续设计。
- 当前 SSOT 的下载前媒体声明 compliant-only 筛选是明确旧合同；改变为考虑加工后可达性属于待传播的规划合同调整，不能作为普通筛选 bug 直接放开所有非合格或 unknown 候选。

## 完整设计草案：双标准下的统一生产规划（2026-09-28）

状态：用户请求完整设计；下文是待 Review 的推荐方案，非实施授权。已确认业务边界以上节为准。本草案归既有 UAT-251，不新建组件计划，不把任何历史已关闭 UAT 自动重开。

### 1. 目标、标准与结果

定义 S0 为当前 Run 冻结的原 Acceptance Spec（由 Shelf Spec 编译）；S1 为由 S0 和版本化次级规则派生的完整次级标准。S1 仅允许 max_size_exceeded 和 metadata.actor 关系缺失；不是任意 Gap 白名单。

S0 永久保留，不能在 S1 阶段改写原 Requirements、评分、成品实测或历史结果。S1 中演员豁免须有本地资料不足且正式 Provider 成功返回无演员的证据；体积豁免须有成功成品实测及质量保护证据。规则定义“哪些可以有条件放宽”；正式接纳绑定“本片哪些放宽条件已成立”。规划可使用有条件目标，授权及 Commit 必须验证条件已成立。

每次最终成品验证都先判断 S0：满足则 on_deck，无须瑕疵授权；否则满足 S1 且所有豁免条件成立，才形成精确瑕疵候选；两者都不满足且没有剩余有界可达路径，结果为 unable_to_on_deck。处于 S1 阶段但偶然达成 S0 时，仍正常入库，不倒退重跑 S0。

“外部寻源耗尽”“未配置 Provider”“某次 Work 失败”只能是路径结果，不能出现在新授权的可豁免类别中。新瑕疵仅为演员关系和体积；旧授权历史仍按原字节保存。

### 2. 统一编排算法

1. 冻结 S0、规划 Policy、当前资料/材料事实及有限处理预算；明确本次仍可执行的路径。
2. 身份和安全前置检查；已证明不可修复的硬性缺口可提前结束，不必先跑所有昂贵动作。
3. 按 S0 评估现有输入和已有成品。直接满足则验证交付；可加工则规划；本地不能补的媒体要求才考虑外部取得。
4. 同一时刻分别保存资料、附件、媒体的进度和缺口。演员确实无资料时记录 S0 的阻断及 S1 条件，不再让这一个字段阻止可完成的海报、NFO和媒体加工。
5. 当 S0 本次不能完整达成（真实业务证据或有界路径终结），评估当前产品能否直接满足 S1。满足则进入授权；不满足但存在可达路径则建立 S1 规划目标；否则安全收尾。
6. 执行 S1 所需的剩余动作，复用有效材料/成果，不为进入 S1 重做已经成功的动作。仍须先按 S0、再按 S1 验证最终成品。
7. 瑕疵授权只发生在实际合格候选成品形成之后。自动关闭不阻止正常规划和有界加工；它只使接纳停在待用户决定。用户仍可主动放弃，走正式收尾。

同一组规划/加工/验证能力服务两个标准。S0/S1 是业务目标的两个阶段，不另建“瑕疵专用转码器”或按影片名编码补救路径。等待资源是过程，不等于不可达；技术重试遵守已有预算，重试耗尽也不能伪造业务无结果。

### 3. 推荐同一个 Libra Run，两个有记录的规划阶段

修正此前“接续新 Run”的初步建议：推荐同一 Subject、同一 Libra Run、同一 Libra Workspace，规划目标从 S0 单向进入 S1，最多一次。原 Acceptance Spec 及已发布 Work/Plan/Result 不变。

理由：这仍是同一次整理、同一原始标准和同一组材料责任。新 Run 会引入跨 Run 的成果引用、Workspace/Control连续性、准入席位和外部下载预算继承，当前需求不需要付出这组额外生命周期复杂度。双标准并不要求覆盖原 Spec，可以以不可变的目标记录和新的 Work Basis 表达。

建议增加 Libra 域内 Planning Target Revision：绑定 runId、S0 ID/digest、tier=primary|secondary、S1 rule revision/digest、触发证据、材料引用集合、前一 revision/digest。目标 Head 通过 CAS 前进；历史记录 append-only。字段和表清单待合同定稿，不直接创建通用过程对象。

S0→S1 之前，使目标相关的旧 Work/Effect 安全停止或收尾。一个原子 Owner 决定保存新 Target、Head、预算继承和后续 Work 意图；不得仅改变内存分支。旧 Work 不可偷偷换目标，新 Work 的幂等身份冻结 Target digest、Source/Intent digest。恢复重放不再建同一 Work，不清空预算、不再寻源。

旧输入和 Workspace 始终由现有 Libra 责任持有；阶段切换不释放 Control、不退回 Procurement、不再次占用 Pre-deck 名额。可复用事实仍核验 Handle、Fence、freshness和对应要求值；需要重新验收时产生新 Result，不改旧失败为成功。

这需要有界修改当前“所有规划目标直接等于 S0”的合同，不声称现有代码已支持。Shelf Standard、身份或材料发生真实变化，继续使用现有 Basis/Freshness/Run替换合同；不能借 S1 接受旧依据，也不借此自动清零本次寻源/生产预算。

### 4. 外部候选按加工后可达性选择

当前证据：`external-material-planner.js` 下载后执行 import/probe/verify，`libra-run-coordinator.js` 在非合格输出满足 `shouldTranscodeExternalImport()` 时已有继续内部转码分支。因此不仅要复用该能力，还必须修正下载前 compliant-only 门禁及 Acquire 端重复门禁。

候选分成四种规划结论：直接可达、加工可达、不可达、证据不足。必须将身份、下载可用性、媒体声明与加工可达性分列，不能统一压成 unavailable。

| 已知事实 | 下载前规划 |
| --- | --- |
| 同片、足够分辨率、合格音轨，HEVC及其他条件已满足 | 直接可达；下载后仍须实检 |
| 同片、足够分辨率、合格音轨，但 H.264 或已知可转换容器 | 加工可达；选择支持该输入的转换路径，不能仅凭非 HEVC 拒绝 |
| 体积超过上限，但允许的编码能力可尝试降到上限 | 可规划加工；预测不是实际成功，也不能直接决定体积豁免 |
| 仅1080p，目标要求4K，且禁止系统放大补足 | 对 S0/S1 均不可达 |
| 只有不合格音轨，目标要求现有能力无法补出的音轨 | 对 S0/S1 均不可达，不通过重编码伪造高质量源 |
| 身份、目标需要的分辨率/音轨或加工所需输入声明未知或互相冲突 | 证据不足；可做有界详情观察补证，未补齐不能通过下载碰运气 |
| 没有正向下载可用性证据或确认无做种 | 下载路径不可用，保留具体原因 |

输入容器、编码等加工前条件不等于最终要求；必须是已知且由注册能力支持的输入，不把任意 unknown 当作可转换。设备暂忙只影响调度；没有任何支持该输入的可用能力则本次路径不可执行。设备 preflight 的最终判定仍在真实媒体取得后完成。

Provider Adapter只解析带来源的客观声明和可用性，不选择业务赢家；Libra Planner以目标要求、转换能力和 Policy 决定可达性。不设通用跨域材料池：只用当前 Run 正式输入、受控 Workspace 成果与冻结候选 Evidence。

首版建议保留现有可达候选集合内的 seederCount DESC、providerRank、candidateId 稳定排序，不同时引入主观画质评分或新的加权成本算法。直接可达与加工可达均有资格，不再要求下载前是最终成品。单来源预算仍适用。

### 5. 两段证据：下载前可规划，下载后才可证明

下载前冻结候选、来源证据、预期可满足要求及必要加工动作，是有依据的可达预期，不是验收通过。下载后沿用正式 External Job、Landing稳定观察、身份/结构验证和 Workspace import；由真实 Probe替换声明进行重新规划。

真实4K/H.264/合格音轨：规划HEVC转码，按现有质量保护与音轨保留规则生产；仅容器不符且其余通过：无损Remux；全部符合：Direct。通常一次转码直接生成最终容器，避免先Remux再无意义二次加工。

真实1080p或缺合格音轨：该材料对两级目标不可达，不能上采样/伪造音轨/放宽次级标准；检查本次已有的其他合法材料是否存在剩余可达路径，不能新下载另一个候选。身份、完整性、安全验证失败的材料不得参与后续产品选择。

对同一媒体重新编码必须使用选定原始输入或已验证外部输入，避免上一轮有损输出成为下一轮重复编码来源；保留达到质量等级的合法成功输出，直到最终选择或安全回收。

### 6. 有限性与资源

- 同一 Run 的 S0/S1 共用一个外部 Acquisition Job额度；切换阶段不增加下载次数。已有搜索快照可在新目标下重新评估尚未取得的候选，但不重复搜索、不突破一个Job。恢复同一Job不算新Job。
- 因本地无法补的媒体要求才寻源；仅体积超限仍不单独触发外部寻源。允许一次寻源得到的素材继续在内部加工。
- 媒体转换以 Source/目标/Intent/Device/Policy 的稳定身份去重；同条件失败和已成功策略不因重新评估再次执行。临时技术重试与业务重新规划使用不同预算。
- 码率策略沿用单调下降及质量下限规则，正式 Encode Intent 使用本次冻结的有限生产 Policy 预算；S0/S1共享，不因换阶段或重启归零。不为次级标准另增一套重试次数。若现有 Policy 缺少可证明终止的边界，合同传播时补齐，不在本业务设计中凭空指定次数。首个Intent即受限于质量保护时，不能为凑次数额外编码；已有技术重试也不能重置硬截止。
- 生产预算耗尽本身不证明可接受体积超限：没有“成功成品仅体积超限 + 后续合规体积码率低于有效质量下限”的证据，只能记录有限处理未完成，不能伪造质量保护资格。
- S1 再优化沿用质量保护，绝不为了满足正常体积上限继续降低相同瑕疵成品的画质；已有合格S1成品无需重编码。
- 收尾遵守 Work/Effect/Control/Workspace现有合同；不可因阶段或终局推进删除仍被引用成品，未决Effect继续恢复。无法入库保留原始媒体；输入删除仍需既有精确授权和Arca正式Settlement。

### 7. 验收、授权与 Arca

Libra输出最终 Product对S0的真实完整差距、S1派生依据、实际验证及精确授权候选。只有所有硬性要求通过且差距恰属于已成立的两类豁免时，才可签发新 Authorized Defect Manifest。

Actor缺失不是NFO缺失：次级产品仍生成有效NFO，其他必填字段完整，只缺对应演员关系。网络失败、未配置或认证失败不证明演员确实无法取得。

自动/手动共用同一资格与提交事务；自动读取当下持续授权Head，手动绑定展示候选及当前revision。关闭自动只阻止新签发，不直接撤销已签发事实。实际成品/差距变化必须重建候选，旧确认不可重放给新成品。

Handoff B仍单向、Arca独立验收：同时验证当前Shelf、原Spec、次级Policy/条件、真实产品、授权和全部安全/Placement条件。Arca不得只看到Manifest字段集合一致就盲信资格，也不依赖调用Libra内部Store判断。缺任何证据即拒绝或按既有有界缺证流程处理，不能倒填成功。

只有Arca On-deck Commit建立收藏事实。已接受瑕疵仍只手动修复；历史安全可播放收藏不因本轮设计自动下架、重编码或重写授权。存量不符合新范围的条目另列清单、另行决定如何修复，不能批量转换旧Manifest成新资格。
